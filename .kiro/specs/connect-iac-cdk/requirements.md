# Requirements Document

Connect IaC (CDK for Python)

## Introduction

The `connect-skills` repository today helps authors research Amazon
Connect and produce configuration artifacts (flows, views, AI agents,
knowledge base content, Lex bots) that are deployed with per-artifact
scripts. It has no Infrastructure-as-Code (IaC) capability: there is no
way to provision the underlying AWS resources — a Connect instance, the
backend APIs and data stores an AI agent calls, the Bedrock AgentCore
gateway that fronts those APIs as an MCP server, or the Connect AI
domain itself — as code.

The `workspace-restructure-iac` spec explicitly deferred this work as
future scope. This spec builds it. It adds an AWS CDK (Python) IaC
capability to the repository along three pillars, each modeled on a
convention that already exists in the repo:

1. **A CDK documentation MCP server** — a second MCP server alongside
   `connect_knowledge`, following the same FastMCP / `uv` / console-script
   pattern, that fetches and serves AWS CDK (Python) reference
   documentation for the construct libraries relevant to Connect work:
   `aws_cdk.aws_connect`, `aws_cdk.aws_lex`, `aws_cdk.aws_wisdom`, and
   `aws_cdk.aws_bedrockagentcore`.

2. **Steering catalogs** — per-domain CDK construct catalogs (Connect,
   Lex, Wisdom/Q in Connect, Bedrock AgentCore) plus one general IaC
   steering file, modeled on the existing `#connect-blocks` /
   `#connect-flow-language` / `#connect-views` catalogs (each entry a
   one-line description plus a link to the specific CDK doc page),
   regenerated by a refresh hook the same way the existing catalogs are.

3. **Skills to scaffold and author CDK projects** — a general IaC skill
   that scaffolds a CDK Python project under a per-project IaC folder and
   authors the constructs that provision the resources a Connect
   deployment needs.

The capability must support provisioning, via CDK, the full chain a
Connect AI self-service deployment depends on: an industry-specific REST
API (API Gateway + OpenAPI schema) backed by Lambdas and DynamoDB; a
Bedrock AgentCore gateway that exposes that REST API as an MCP server;
a Connect instance; a Q in Connect (Wisdom) domain and assistant; a
knowledge base integration backed by S3 documents; the MCP, Lex, and
Lambda integrations associated to the instance; flows and views; AI
agents, prompts, guardrails, and tools; and security profiles.

Because authors frequently already have parts of this chain in place —
for example a working Connect instance or an existing AgentCore gateway
MCP server — the capability is conditional rather than always-create: it
references resources that already exist (when their identifiers are
supplied) and only provisions the resources that are missing, unless the
operator explicitly asks to create a new one.

### Alignment with existing conventions (non-functional baseline)

This capability reuses the repository's established structure rather
than inventing a parallel one:

- Skills live in `.kiro/skills/<name>/` with a `SKILL.md` and
  self-contained scripts.
- Steering lives in `.kiro/steering/*.md` with `inclusion: manual`,
  front matter recording `last_refreshed` + source URLs + checksum, and
  a 7-day freshness rule the agent enforces.
- MCP servers follow the `connect_knowledge_mcp/` pattern (FastMCP, `uv`,
  console scripts, registered in `.kiro/settings/mcp.json`).
- Refresh hooks (`.kiro/hooks/*.kiro.hook` + `.kiro/hooks/scripts/`)
  regenerate the steering catalogs.
- Concrete deliverables live under `projects/<project>/`; this spec adds
  a `projects/<project>/<project>-cdk/` IaC subfolder.

### Security baseline (cross-cutting)

No AWS credentials, account IDs tied to a live account, secrets, or
session tokens are ever written into any generated artifact, skill,
steering file, or spec document. All AWS access resolves from the
operator's local AWS profile / SSO environment at deploy time.

## Glossary

- **CDK**: AWS Cloud Development Kit for Python — the IaC framework this
  capability uses to define AWS resources as code.
- **CDK_Project**: a CDK application for one project, located at
  `projects/<project_name>/<project_name>-cdk/`.
- **CDK_Docs_MCP**: the new MCP server that fetches and serves AWS CDK
  (Python) reference documentation for the in-scope construct libraries.
- **CDK_Docs_Refresh**: the hook-invoked script that regenerates the CDK
  steering catalogs from the CDK documentation.
- **IaC_Skill**: the Kiro skill that scaffolds and authors a
  `CDK_Project`.
- **IaC_Steering**: the set of CDK construct catalog steering files (one
  per domain plus one general IaC file).
- **Construct_Library**: an `aws_cdk.aws_*` Python module in scope:
  `aws_cdk.aws_connect`, `aws_cdk.aws_lex`, `aws_cdk.aws_wisdom`,
  `aws_cdk.aws_bedrockagentcore`.
- **AgentCore_Gateway**: an Amazon Bedrock AgentCore gateway resource
  that exposes a backend (here, a REST API described by an OpenAPI
  schema) as an MCP server.
- **MCP_Server_Backend**: an MCP server created by an `AgentCore_Gateway`
  (e.g. `anycompany-hotels-mcp-server`) that a Connect AI agent consumes
  as an MCP tool integration.
- **MCP_Integration**: a Connect AI agent tool integration that points at
  an `MCP_Server_Backend`.
- **Q_in_Connect**: Amazon Q in Connect (the Wisdom-backed AI domain and
  assistant feature of Amazon Connect).
- **REST_API**: an Amazon API Gateway REST API described by an OpenAPI
  schema.
- **Existing_Resource_Identifier**: an externally-supplied identifier or
  ARN for an AWS resource that already exists (for example an existing
  Connect instance ID/ARN, an existing `AgentCore_Gateway` /
  `MCP_Server_Backend` ID/ARN, an existing `Q_in_Connect` domain ID, an
  existing knowledge base ID, or an existing Lex bot ID/ARN), passed into
  the `CDK_Project` as configuration so that dependent constructs bind to
  the existing resource instead of provisioning a new one.
- **Operator**: the human running a deploy from their local environment.
- **AWS_Profile**: the local AWS credentials/SSO configuration the
  `Operator` is authenticated with.

## Requirements

### Requirement 1: CDK documentation MCP server

**User Story:** As a Connect IaC author, I want an MCP server that serves
AWS CDK (Python) reference documentation, so that I can ground construct
choices in canonical CDK docs without leaving the workspace.

#### Acceptance Criteria

1. THE CDK_Docs_MCP SHALL be implemented as a FastMCP server following
   the `connect_knowledge_mcp` pattern (a `pyproject.toml` declaring a
   `uv`-runnable entrypoint and any console scripts).
2. THE CDK_Docs_MCP SHALL expose a search tool that accepts a free-text
   query and returns matching CDK documentation results formatted as
   title, URL, and snippet.
3. THE CDK_Docs_MCP SHALL expose a per-construct deep-dive tool that
   accepts a construct identifier and returns that construct's parsed
   documentation, including its properties and a link to the source CDK
   doc page.
4. THE CDK_Docs_MCP SHALL serve documentation for each Construct_Library
   in scope: `aws_cdk.aws_connect`, `aws_cdk.aws_lex`,
   `aws_cdk.aws_wisdom`, and `aws_cdk.aws_bedrockagentcore`.
5. WHEN the CDK_Docs_MCP fetches a documentation page, THE CDK_Docs_MCP
   SHALL parse the page into a structured result that preserves the
   construct name, the property list, and the source URL.
6. IF a requested construct or documentation page cannot be retrieved or
   parsed, THEN THE CDK_Docs_MCP SHALL return a descriptive error result
   that names the requested identifier and the reason.
7. WHERE the CDK_Docs_MCP exposes a console script, THE CDK_Docs_MCP
   SHALL run the same lookup from a terminal and produce output
   equivalent to the MCP tool result.

### Requirement 2: CDK documentation MCP registration

**User Story:** As a maintainer, I want the CDK docs MCP server
registered alongside the existing server, so that the tools appear in the
MCP client without manual wiring.

#### Acceptance Criteria

1. THE SYSTEM SHALL register the CDK_Docs_MCP in
   `.kiro/settings/mcp.json` as an additional server entry without
   altering the existing `connect_knowledge` server entry.
2. THE SYSTEM SHALL declare the CDK_Docs_MCP read-only tools in the
   server entry's `autoApprove` list.
3. WHEN the CDK_Docs_MCP server entry is added, THE SYSTEM SHALL resolve
   the server directory and the `uv` binary as absolute paths consistent
   with the existing `connect_knowledge` entry.
4. THE SYSTEM SHALL register the CDK_Docs_MCP server entry before its
   tools are declared available to the MCP client.

### Requirement 3: CDK steering catalogs

**User Story:** As a Connect IaC author, I want per-domain catalogs of
the CDK constructs I can create, so that I can pick constructs the same
way I pick flow blocks today.

#### Acceptance Criteria

1. THE IaC_Steering SHALL provide one CDK construct catalog steering file
   per domain: Connect, Lex, Q_in_Connect (Wisdom), and Bedrock
   AgentCore.
2. THE IaC_Steering SHALL provide one general IaC steering file covering
   CDK project conventions, the project-folder layout, and the
   bootstrap/deploy workflow.
3. THE IaC_Steering SHALL represent each construct as a catalog entry
   containing the construct name, a one-line description, and a link to
   the construct's CDK documentation page.
4. THE IaC_Steering SHALL set `inclusion: manual` in each steering file's
   front matter.
5. THE IaC_Steering SHALL record in each steering file's front matter the
   `last_refreshed` date, the source URLs, and a content checksum.
6. WHILE a steering file's `last_refreshed` date is more than 7 days
   before the current date, THE IaC_Steering SHALL instruct the agent to
   run CDK_Docs_Refresh before relying on the catalog.

### Requirement 4: CDK steering refresh hook

**User Story:** As a maintainer, I want the CDK catalogs regenerated by a
hook the same way the existing catalogs are, so that keeping them current
is a single command.

#### Acceptance Criteria

1. THE CDK_Docs_Refresh SHALL regenerate the IaC_Steering catalog files
   from the CDK documentation source pages.
2. THE SYSTEM SHALL provide a `.kiro.hook` definition that invokes
   CDK_Docs_Refresh, following the existing `refresh-*.kiro.hook` pattern.
3. WHEN CDK_Docs_Refresh regenerates a steering file, THE
   CDK_Docs_Refresh SHALL update that file's `last_refreshed` date and
   content checksum.
4. WHERE CDK_Docs_Refresh is invoked with a dry-run option, THE
   CDK_Docs_Refresh SHALL report the changes it would make without
   writing the steering files.
5. IF a CDK documentation source page cannot be fetched during a refresh,
   THEN THE CDK_Docs_Refresh SHALL report the failing source URL and
   leave the previously generated steering file unchanged.

### Requirement 5: IaC project scaffolding skill

**User Story:** As a Connect IaC author, I want a skill that scaffolds a
CDK Python project for a project, so that every IaC deliverable starts
from a consistent, deployable layout.

#### Acceptance Criteria

1. THE IaC_Skill SHALL be a self-contained Kiro skill in
   `.kiro/skills/<name>/` containing a `SKILL.md` and any scripts the
   skill drives.
2. WHEN the IaC_Skill scaffolds a project, THE IaC_Skill SHALL create the
   CDK application under `projects/<project_name>/<project_name>-cdk/`.
3. THE IaC_Skill SHALL organize constructs into per-resource-type
   subfolders within the CDK_Project (for example `lambda/` for Lambda
   constructs, `databases/` for data-store constructs, and `apis/` for
   API constructs), following the referenced primitive-repo layout
   convention.
4. WHEN the IaC_Skill bootstraps the CDK_Project, THE IaC_Skill SHALL
   produce a Python CDK application that installs its dependencies into a
   project-local virtual environment from a pinned requirements
   declaration.
5. WHERE the IaC_Skill scaffolds the CDK_Project via the CDK CLI (one
   supported scaffolding option the IaC_Skill MAY choose, including when
   the CDK CLI is available), THE IaC_Skill SHALL run
   `cdk init app --language=python` and then create the project-local
   virtual environment and install dependencies from the pinned
   requirements declaration (per criterion 4).
6. WHERE the IaC_Skill scaffolds the CDK_Project manually (a permitted
   scaffolding option the IaC_Skill MAY choose whether or not the CDK CLI
   is available, including when the CDK CLI is unavailable), THE
   IaC_Skill SHALL build the equivalent CDK_Project structure with the
   same project-local virtual environment installed from the pinned
   requirements declaration (per criterion 4).
7. THE IaC_Skill SHALL produce a `CDK_Project` whose `cdk synth`
   completes without error before the scaffold step is reported complete.

### Requirement 6: Conditional provisioning of existing resources (reuse vs create)

**User Story:** As a Connect IaC author, I want the IaC capability to
reuse resources that already exist and only create the ones that are
missing, so that I can layer new infrastructure onto an existing Connect
instance or AgentCore gateway without duplicating or disrupting working
resources.

#### Acceptance Criteria

1. WHERE a required resource (Connect instance, AgentCore_Gateway /
   MCP_Server_Backend, Q_in_Connect domain, knowledge base, Lex bot, or
   another in-scope dependency) already exists and its
   Existing_Resource_Identifier is supplied, THE IaC_Skill SHALL
   reference the existing resource (via CDK import / lookup /
   `from*Attributes` / `fromArn`-style references or a passed-in
   identifier parameter) rather than provisioning a new one.
2. WHEN no Existing_Resource_Identifier is supplied for a required
   dependency, THE IaC_Skill SHALL provision a new resource for that
   dependency.
3. WHERE the Operator explicitly requests creation of a new resource even
   though a matching resource already exists, THE IaC_Skill SHALL
   provision a new resource as requested.
4. THE CDK_Project SHALL expose configuration (CDK context or stack
   parameters) for supplying Existing_Resource_Identifier values (for
   example existing Connect instance ID/ARN, existing AgentCore_Gateway
   ID/ARN, and existing Q_in_Connect domain ID) so that dependent
   constructs bind to the supplied existing resources.
5. WHEN a dependent construct is generated, THE IaC_Skill SHALL bind that
   construct to whichever resource — existing (referenced) or new
   (provisioned) — is in use for the required dependency.
6. IF a supplied Existing_Resource_Identifier cannot be resolved to a
   reachable resource, THEN THE IaC_Skill SHALL report the unresolved
   identifier and SHALL NOT provision a duplicate resource in its place.

### Requirement 7: Backend application infrastructure (REST API, Lambda, data)

**User Story:** As a Connect IaC author, I want to provision an
industry-specific REST API with its backend Lambdas and tables, so that a
Connect AI agent has a real backend to call.

#### Acceptance Criteria

1. WHERE a project requires a backend API, THE IaC_Skill SHALL generate a
   CDK construct that provisions an Amazon API Gateway REST_API described
   by an OpenAPI schema for the project's industry domain (for example
   hotels, bookings, flights, or appointments).
2. WHERE a project requires backend compute, THE IaC_Skill SHALL generate
   CDK constructs that provision the AWS Lambda functions backing the
   REST_API operations.
3. WHERE a project requires persistent storage, THE IaC_Skill SHALL
   generate CDK constructs that provision the Amazon DynamoDB tables the
   backend Lambdas read and write.
4. THE IaC_Skill SHALL store the REST_API OpenAPI schema as a project
   artifact within the CDK_Project.
5. IF the REST_API construct cannot be generated because the project's
   industry-domain configuration is missing or invalid, THEN THE
   IaC_Skill SHALL report the invalid configuration and SHALL generate a
   minimal valid REST_API construct scaffold that synthesizes without
   error.

### Requirement 8: Bedrock AgentCore gateway as an MCP server

**User Story:** As a Connect IaC author, I want to provision a Bedrock
AgentCore gateway that exposes a REST API as an MCP server, so that the
backend becomes an MCP tool a Connect AI agent can use.

#### Acceptance Criteria

1. WHERE a project requires an MCP server backend and no existing
   AgentCore_Gateway / MCP_Server_Backend Existing_Resource_Identifier is
   supplied, THE IaC_Skill SHALL generate a CDK construct that provisions
   an AgentCore_Gateway.
2. WHERE an existing AgentCore_Gateway / MCP_Server_Backend
   Existing_Resource_Identifier is supplied, THE IaC_Skill SHALL bind to
   the existing gateway / MCP server backend rather than provisioning a
   new one.
3. WHEN the IaC_Skill provisions a new AgentCore_Gateway, THE IaC_Skill
   SHALL configure the AgentCore_Gateway with a target of type REST API
   whose tool surface is defined by an OpenAPI schema.
4. WHERE the OpenAPI schema is provided from object storage, THE
   IaC_Skill SHALL configure the AgentCore_Gateway target to read the
   schema from its Amazon S3 location.
5. WHEN the IaC_Skill provisions a new AgentCore_Gateway, THE IaC_Skill
   SHALL configure the AgentCore_Gateway inbound authorization with a
   discovery URL derived from the target Connect instance's OpenID
   configuration endpoint
   (`https://<instance-alias>.my.connect.aws/.well-known/openid-configuration`)
   and an allowed audience set to the gateway identifier.
6. WHEN the AgentCore_Gateway is in use (newly provisioned or referenced
   from an existing one), THE IaC_Skill SHALL expose the resulting
   MCP_Server_Backend so that it can be wired as an MCP_Integration for a
   Connect AI agent.

### Requirement 9: Connect instance provisioning

**User Story:** As a Connect IaC author, I want to provision a new
Connect instance as code or reference an existing working instance, so
that an environment can be stood up repeatably or extended in place.

#### Acceptance Criteria

1. WHERE a project requires a contact center and no existing Connect
   instance Existing_Resource_Identifier is supplied, THE IaC_Skill SHALL
   generate a CDK construct that provisions an Amazon Connect instance.
2. WHERE an existing Connect instance Existing_Resource_Identifier
   (instance ID or ARN) is supplied, THE IaC_Skill SHALL reference the
   existing Connect instance rather than provisioning a new one.
3. THE IaC_Skill SHALL expose the Connect instance's identifier — whether
   newly provisioned or referenced from an existing instance — so that
   dependent constructs can associate resources to it.

### Requirement 10: Q in Connect domain, assistant, and knowledge base

**User Story:** As a Connect IaC author, I want to provision the Q in
Connect domain, assistant, and a knowledge base backed by S3 documents,
or reuse existing ones, so that the AI agent has a retrieval surface as
code.

#### Acceptance Criteria

1. WHERE a project requires AI assistance and no existing Q_in_Connect
   domain Existing_Resource_Identifier is supplied, THE IaC_Skill SHALL
   generate a CDK construct that provisions a Q_in_Connect domain and
   assistant.
2. WHERE an existing Q_in_Connect domain Existing_Resource_Identifier is
   supplied, THE IaC_Skill SHALL reference the existing Q_in_Connect
   domain and assistant rather than provisioning new ones.
3. WHERE a project requires retrieval and no existing knowledge base
   Existing_Resource_Identifier is supplied, THE IaC_Skill SHALL generate
   a CDK construct that provisions a knowledge base integration backed by
   an Amazon S3 source containing the project's documents.
4. WHERE an existing knowledge base Existing_Resource_Identifier is
   supplied, THE IaC_Skill SHALL reference the existing knowledge base
   rather than provisioning a new one.
5. WHEN the knowledge base integration is in use (newly provisioned or
   referenced), THE IaC_Skill SHALL associate the knowledge base with the
   Q_in_Connect domain in use.

### Requirement 11: Instance integrations (MCP, Lex, Lambda)

**User Story:** As a Connect IaC author, I want to associate MCP, Lex,
and Lambda integrations to the Connect instance, so that the agent and
flows can invoke them.

#### Acceptance Criteria

1. WHERE a project uses an MCP_Server_Backend, THE IaC_Skill SHALL
   generate a CDK construct that creates an MCP_Integration for the
   Connect AI agent against the Connect instance in use.
2. WHERE a project uses a Lex bot and no existing Lex bot
   Existing_Resource_Identifier is supplied, THE IaC_Skill SHALL generate
   a CDK construct that provisions the Lex bot and associates it with the
   Connect instance in use.
3. WHERE an existing Lex bot Existing_Resource_Identifier is supplied,
   THE IaC_Skill SHALL reference the existing Lex bot and associate it
   with the Connect instance in use rather than provisioning a new bot.
4. WHERE a project uses backend Lambda functions in flows, THE IaC_Skill
   SHALL generate a CDK construct that associates each Lambda function
   with the Connect instance in use.

### Requirement 12: Connect experience artifacts (flows and views)

**User Story:** As a Connect IaC author, I want flows and views
provisioned as code, so that the experience layer deploys with the rest
of the stack.

#### Acceptance Criteria

1. WHERE a project includes contact flows, THE IaC_Skill SHALL generate a
   CDK construct that provisions each contact flow on the Connect
   instance in use.
2. WHERE a project includes views, THE IaC_Skill SHALL generate a CDK
   construct that provisions each view on the Connect instance in use.

### Requirement 13: Connect AI agents, prompts, guardrails, and tools

**User Story:** As a Connect IaC author, I want AI agents and their
prompts, guardrails, and tools provisioned as code, so that the agent
configuration is reproducible.

#### Acceptance Criteria

1. WHERE a project includes an AI agent, THE IaC_Skill SHALL generate a
   CDK construct that provisions the Connect AI agent.
2. WHERE an AI agent uses custom prompts, THE IaC_Skill SHALL generate a
   CDK construct that provisions each AI prompt.
3. WHERE an AI agent uses a guardrail, THE IaC_Skill SHALL generate a CDK
   construct that provisions the guardrail.
4. WHERE an AI agent uses tools, THE IaC_Skill SHALL generate a CDK
   construct that provisions each AI agent tool, including
   MCP_Integration tools.

### Requirement 14: Security profiles

**User Story:** As a Connect IaC author, I want security profiles
provisioned as code, so that agent permissions are part of the
reproducible stack.

#### Acceptance Criteria

1. WHERE a project requires agent permissions, THE IaC_Skill SHALL
   generate a CDK construct that provisions each Connect security
   profile.

### Requirement 15: Credential handling

**User Story:** As an Operator, I want all AWS access to come from my
local profile, so that no credentials are ever committed to the
repository.

#### Acceptance Criteria

1. THE IaC_Skill SHALL resolve AWS credentials from the Operator's
   AWS_Profile / SSO environment at deploy time.
2. THE SYSTEM SHALL exclude AWS credentials, secret access keys, and
   session tokens from every generated artifact, skill, steering file,
   and spec document.
3. IF a deploy is attempted without resolvable AWS credentials, THEN THE
   IaC_Skill SHALL report that credentials are missing and SHALL NOT
   write any credential material into the CDK_Project.

### Requirement 16: Deployment and verification workflow

**User Story:** As a Connect IaC author, I want to preview and deploy a
CDK_Project safely, so that I can validate before provisioning live
resources.

#### Acceptance Criteria

1. THE IaC_Skill SHALL document the bootstrap, synth, diff, and deploy
   commands for the CDK_Project in its `SKILL.md`.
2. WHEN the IaC_Skill prepares a deployment, THE IaC_Skill SHALL run
   `cdk synth` and SHALL report any synthesis error before any deploy
   step.
3. WHERE a preview is requested, THE IaC_Skill SHALL run `cdk diff`
   against the deployed stack and present the difference before
   provisioning.

### Requirement 17: Scope boundary and documentation

**User Story:** As a maintainer, I want the IaC capability to extend the
repository without duplicating existing skills, and to be documented in
the README, so that contributors know where it fits.

#### Acceptance Criteria

1. THE IaC_Skill SHALL reuse the existing artifact authoring skills
   (`connect-flow-author`, `connect-view-author`, `connect-ai-agent-author`,
   `connect-kb-author`, `q-in-connect-bot-deploy`) for designing
   artifact bodies, and SHALL consume their outputs rather than
   re-authoring those artifacts.
2. THE SYSTEM SHALL update the root `README.md` to document the
   CDK_Docs_MCP server, the IaC_Steering catalogs, and the IaC_Skill.
3. THE SYSTEM SHALL leave the existing `connect_knowledge` MCP server,
   its tools, the existing steering catalogs, and the existing skills
   functional and unchanged in behavior.

## Non-functional / cross-cutting

1. **Convention reuse**: the CDK_Docs_MCP, IaC_Steering, IaC_Skill, and
   refresh hook follow the existing repository patterns for MCP servers,
   steering files, skills, and hooks respectively.
2. **No secrets in the repo**: no credentials, secret keys, session
   tokens, or live-account-bound secrets appear in any committed file.
3. **Synth-before-deploy**: every CDK_Project is validated with
   `cdk synth` before any deploy, and previewed with `cdk diff` on
   request.
4. **Reference layout**: the CDK_Project layout follows the referenced
   primitive repositories (per-resource-type subfolders) and the
   `projects/<project>/<project>-cdk/` convention.
5. **No regression**: every existing skill, hook, MCP tool, CLI, and
   deploy script that works before this change works after it.
6. **Reuse before create**: across every provisioning requirement, the
   capability references an already-existing resource when its
   Existing_Resource_Identifier is supplied and only provisions a new
   resource when none is supplied, unless the Operator explicitly
   requests creating a new one.
